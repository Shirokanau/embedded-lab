## ① 8051 单片机电子密码锁

**一句话**：用 **1ms 定时器中断**作为全系统时基，把所有延时做成非阻塞软件计时器，主循环只处理按键事件与状态判断的密码锁实现（`CX.c`，426 行，含完整中文注释）。

- **硬件**：AT89C51 + 4×4 矩阵键盘（P1）+ 4 位数码管（P0 段码 / P2.0-P2.3 位选）+ 蜂鸣器（P3.1）+ LED（P3.0）
- **功能**：密码输入（逐位显示 `8` 遮蔽）、校验、修改、回删、**输入超时 10s 报警**、**错误后 3s 冷却**、**连续三次错误键盘锁定**、万用开锁 30s 自动上锁
- **关键实现**：
  - 定时器 T0 模式 1，`TH0=(65536-1000)/256` → 1ms 中断；中断内并行管理 5 组软件计时器，并**把数码管动态扫描放进中断**保证刷新周期稳定
  - 矩阵键盘行列反转扫描：`P1=0xf0` 判按下 → `delay(10)` 消抖 → 反转读列 → 查表得键值；静态变量防连发
  - 用状态标志位（`password_wrong_flag`、`LED_Flashnum`、`Close_Lock_time` 等）替代 `delay()` 实现多任务时间逻辑
- **产物**：源码、Keil 工程、Proteus 仿真原理图、可直接烧录的 `hex`、课程设计报告
- ⚠️ 已知问题（含 3 次错误后的死循环锁定、回删时的下标下溢）已在子 README 中逐条列出，**代码保持原样未修改**

→ 详见 [`01-8051-electronic-lock/README.md`](01-8051-electronic-lock/README.md)

## ② 传感器数据采集与分析

**一句话**：从串口把 DHT11 / HC-SR04 / MPU-6050 三类传感器的实测数据读进来，做异常检测、滤波降噪、姿态解算与回归建模，并用 RMSE/MAE/MAPE 与 5 折交叉验证量化评估。

- **数据采集**：温湿度/姿态 **115200**、超声波 **38400**，统一 **8N1**；验证无乱码，确认波特率匹配的重要性
- **预处理**：Z-Score(2.5) / IQR(1.5) / 3-Sigma → 线性插值修复 → 移动平均(w=5) / 指数平滑(α=0.3) / Savitzky-Golay(w=7,order=3) / **自写卡尔曼(Q=0.01, R=1.0, P=1.0)**
- **姿态解算**：陀螺仪零偏校准 → 加速度计低通 5Hz + 陀螺仪高通 0.5Hz → **互补滤波 α=0.96**
- **机器学习**：时间/滚动/滞后/交互特征工程 → `SelectKBest(k=15)` → 8 类模型（含 RF、GB、SVR、MLP）→ 5 折交叉验证 → Top-3 加权融合
- **结果（HC-SR04 真实采集 490 组）**：卡尔曼滤波后 RMSE 0.3076 cm / MAE 0.2377 cm

> ### ⚠️ 关于数据真实性的说明（重要）
> 我在这里把话说清楚，因为这关系到这段经历能不能经得起追问：
> - `hcsr04_preprocessing_demo.py`、`dht11_preprocessing_demo.py` 读的是**真实采集的 Excel**；
> - `mpu6050_preprocessing_demo.py` 与两个 DHT11 机器学习脚本是**脚本内生成仿真数据**（代码里有 `seed` 与注释掉的旧模拟代码为证），仓库中已逐条标注；
> - `reports/MPU-6050预处理报告.txt` 里那个"性能提升 −621.8%"是**仿真数据下的真实计算结果**（互补滤波反而差于纯加速度计），原因是零偏估计的"前 100 样本静止"假设在动态数据上不成立——我把它保留下来，因为**误差来源分析比漂亮的指标更有价值**；
> - HC-SR04 报告的"RMSE 降低 91.6%"里，脚本的"真实值"取的是**清洗后数据的均值**（`np.mean(cleaned)`），**不等于独立测量的真值**，因此它只能证明滤波平滑效果，不能直接等同于测距精度提升。这一点我在子 README 里也标注了。

→ 详见 [`02-sensor-data-analysis/README.md`](02-sensor-data-analysis/README.md)
